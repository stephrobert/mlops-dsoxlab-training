## m1-registre-alias : VALIDE (avant 0/4, apres 4/4, rejeu 0/4, 40 s)

- `mlflow.register_model("models:/<model_id>", nom)` : la version porte `run_id` et `source=models:/m-...` ; `set_registered_model_alias` et `get_model_version_by_alias` fonctionnent. Un script interrompu laisse des versions creees (1,2 puis 3,4) : les tests raisonnent sur l'etat, jamais sur un numero fixe.
- Stages en 3.17.1 : `transition_model_version_stage` et `get_latest_versions` marchent encore mais emettent un FutureWarning ("deprecated since 2.9.0. Model registry stages will be removed in a future major release"). Le lab n'enseigne que les alias ; un test exige que toutes les versions restent en stage `None`.
- PIEGE (cause et parade, a citer dans la lecon) : `mlflow.sklearn.load_model("models:/nom@champion")` reste suspendu (plus de 90 s) sur `model.skops` (18 Mo). Cause : le serveur annonce par `/server-info` qu'il sait servir le telechargement multipart ; le client demande alors une URL presignee et telecharge par morceaux directement chez S3, a l'adresse interne `http://garage:3900`, injoignable depuis l'hote. `curl` du meme fichier par `/api/2.0/mlflow-artifacts/artifacts/...` rend 200 en 0,06 s. Parade cote client : `MLFLOW_ENABLE_PROXY_MULTIPART_DOWNLOAD=false` (chargement en 0,9 s). `MLFLOW_ENABLE_MULTIPART_DOWNLOAD=false` N'AGIT PAS sur ce chemin (essaye, toujours suspendu). Le serveur 3.17.1 n'offre pas d'interrupteur cote serveur reperage dans handlers.py. Le seuil de taille (`MLFLOW_MULTIPART_DOWNLOAD_MINIMUM_FILE_SIZE`) n'est pas la cause ici.
- Charge par alias : `mlflow.sklearn.load_model("models:/latence-service@challenger")` puis `predict(np.array([[60,70,150,0.02]]))`.

## m1-tests-modele : VALIDE (avant 0/5, apres 5/5, rejeu 0/5, 27 s, sans Docker)

- Fixtures : `casse-schema.csv` (colonne `memoire_pct` renommee `mem_pct`), `casse-bornes.csv` (cpu 140, taux_erreur -0.5, requetes_s -12, latence 0 ; schema intact), 60 lignes chacun ; `train.py --arbres N --sortie chemin`.
- Le controle fabrique lui-meme les modeles et rejoue la suite de l'apprenant avec `DONNEES`, `MODELE`, `CHAMPION` : RMSE mesures sur le decoupage 0,2 / graine 42 des 5000 lignes : 100 arbres 22,41 ; 50 arbres 23,31 ; 10 arbres 24,30 ; 3 arbres 27,41 ; 50 arbres profondeur 4 : 27,48 ; profondeur 2 : 30,41. Seuil `rmse_max: 28.0`, tolerance au champion 1,0 ms : le modele a 10 arbres (24,30) passe le seuil absolu mais est refuse par la comparaison au champion (22,41 + 1,0) ; la profondeur 2 est refusee par le seuil. Les deux garde-fous sont donc testes separement.
- PIEGE de harnais : sans test collecte, pytest rend 5 (pas 0 ni 1). Un controle « la suite doit echouer » qui accepte tout code non nul serait vert avant tout travail ; il exige donc 1 ou 2 et le mot failed/error dans la sortie.
- Choix de l'outil de validation des donnees (essai fait, pandas 3.0.6, pytest, pandera 0.34.1) : assertions pandas dans pytest. Cout de pandera : +11 Mo dans le venv (255 -> 266 Mo), +4 dependances (pydantic 2.14.1, pydantic-core, typeguard 4.6.0, typing-inspect), import 0,10 s en plus de pandas 0,18 s. Benefice reel : `lazy=True` rend toutes les erreurs d'un coup (schema : 1 cas `column_in_dataframe` ; bornes : 4 cas `in_range(0, 1)`, `in_range(0, 100)`, `greater_than_or_equal_to(0)`, `greater_than(0)`), alors qu'un `assert` s'arrete au premier. Choix : assertions pandas pour le lab et la lecon (zero dependance, schema de 5 colonnes, le controle est agnostique de l'outil) ; pandera cite comme etape suivante quand le schema grossit. Evidently n'est pas essaye (M8).
- Le lab n'utilise pas DVC ni MLflow : le seuil est lu dans `seuils.yaml` (versionne).
